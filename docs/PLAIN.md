# 白話版：每一關到底在幹嘛

> 正式的說明在 `LEARNING.md`，很詳細但很硬。這份是「先讓你知道這關在解決什麼問題」，一關三到五句話，用同一個比喻講完。
> 看完這份再去看 `LEARNING.md` 對應的關卡，會輕鬆很多。卡住的時候也先回來這裡。
> 真的要動手：請 AI 照 `COACHING.md` 那一關的腳本帶你，一次一個指令。

## 比喻：一家會員制的店

整個專案就是一家店：

| 程式裡的東西 | 比喻 |
| --- | --- |
| 前端（React） | **櫃台**。客人看得到、會互動的地方 |
| 後端（FastAPI） | **店本身**。真正決定「能不能進、能拿什麼」的地方 |
| 資料庫（Postgres） | **倉庫**。會員名冊、會員卡紀錄都放這裡 |
| access token | **當天通行證**。30 分鐘就作廢，每次進門都要出示，店員看一眼就放行，不用翻名冊 |
| refresh token | **會員卡**。7 天有效，只在「換通行證」的時候拿出來，店員會翻名冊核對 |
| 登入 | 櫃台核對密碼 → 發一張通行證 + 一張會員卡 |
| refresh | 通行證過期了，拿會員卡換一張新的通行證（而且會員卡也換新的） |

為什麼要兩張？只有一張的話，要嘛太短命（一直要重新登入），要嘛太長命（被偷了可以用很久）。通行證短命、被偷損失有限；會員卡長命，但店裡有紀錄、可以作廢。

## 關卡 0：密碼規則

**情境**：有人用中文當密碼，店的系統當場當機（500）。
**做了什麼**：規定密碼只能用英文、數字、符號，8 到 72 個字，不符合的在櫃台就擋掉，不讓它進到後面。
**為什麼重要**：加密密碼的工具（bcrypt）只看前 72 個 byte，中文一個字佔 3 個，24 個字就滿了，後面的字根本沒被檢查。與其默默截掉，不如老實告訴客人。

## 關卡 1：會員卡輪替

**情境**：會員卡被偷了，小偷可以用 7 天，你完全不知道。
**做了什麼**：每次拿會員卡換通行證，舊卡立刻作廢、發一張新卡。如果有人拿「已經作廢的卡」來，代表那張卡被偷過（正常人手上只會有最新的），店就把這個會員**所有的卡**全部作廢，大家重新登入，小偷手上的新卡也失效。
**順便**：倉庫裡不存會員卡本身，只存卡的「指紋」（雜湊）。倉庫被偷，小偷拿到的也只是指紋，不能拿去用。
**前端要配合**：畫面同時發三個請求都要換卡時，只能派一個人去換，其他人等結果（single-flight）。不然第二個人拿著剛作廢的舊卡去換，就被當成小偷。

## 關卡 2：設定抽出來

**情境**：資料庫密碼直接寫在程式碼裡，推上 GitHub 等於公開。
**做了什麼**：所有「會因環境不同而不同」的東西（資料庫在哪、簽通行證的密鑰、有效期多長）集中到一個 `.env` 檔，程式啟動時讀；`.env` 不進 git。少填一個，店直接開不了門，而且會告訴你少了哪個。
**為什麼重要**：「啟動時就壞」比「某個客人來了才壞」好一百倍。

## 關卡 3：登出所有裝置、改密碼

**情境**：手機掉了，上面還登入著。
**做了什麼**：「登出所有裝置」就是把這個會員的所有會員卡作廢。「改密碼」也會這樣做（密碼多半是因為外洩才改的），但會立刻給你現在這台一張新卡，你不用重新登入。
**限制**：別台裝置手上的通行證在 30 分鐘內還能用，因為店員看通行證不翻名冊。這是刻意的取捨。

## 關卡 4：自動化測試

**情境**：每改一點東西就要手動點一遍註冊、登入、換卡、登出，而且還是會漏。
**做了什麼**：把「手動點點看」寫成程式，一個指令跑完所有情境。用一個獨立的測試倉庫，每個情境開始前清空，互不影響。
**為什麼重要**：之後的每一關都靠它確認「沒把前面的東西改壞」。

## 關卡 5：資料庫遷移

**情境**：倉庫要多加一個欄位（最後登入時間），以前的做法是「整個倉庫砍掉重建」，正式環境不可能這樣做。
**做了什麼**：改用 Alembic，每次改倉庫結構就產生一份「施工單」（遷移檔），記錄從上一版到這一版要做什麼，倉庫照單施工。施工單進 git，所有人、所有環境的倉庫長得一樣。
**規矩**：改了表的定義一定要產生施工單；已經施工過的單子不能改，要改就開新單。

## 關卡 6：前端整理

**情境**：櫃台的程式碼全塞在一個檔案裡，要搬到別的專案不知道從哪剪。
**做了什麼**：拆成三塊：「跟店講話的方式」（api/）、「記住誰登入了、怎麼登入登出」（auth/）、「畫面」（components/）。之後新專案要登入功能，複製前兩塊就好。

## 關卡 7：多頁面與守門員

**情境**：店要有登入頁、首頁、設定頁，而且沒登入的人不能進首頁。
**做了什麼**：用 React Router 做多頁面；寫兩個守門員：一個擋「沒登入的人」（導去登入頁，還記得你本來要去哪），一個擋「已登入的人」（不用再看登入頁）。
**重點**：櫃台的守門員只是體驗，真正把關的是店（後端）。櫃台的檢查任何人都繞得過。

## 關卡 8：換成套件

**情境**：第 6 關手寫的「記住誰登入」和「自動帶通行證、過期自動換卡」能用，但業界有現成的工具。
**做了什麼**：記住狀態改用 Zustand，跟店講話改用 axios 的攔截器（每個請求送出前自動貼通行證，收到 401 自動換卡重送）。畫面一行都不用改，因為第 6 關有分層。
**為什麼先手寫再換**：手寫過，才知道套件幫你做了什麼，壞掉時知道去哪找。

## 關卡 9：Docker 與 CI

**情境**：「我這邊好好的，你那邊壞了」。
**做了什麼**：把店打包成一個 image（連作業系統、Python、套件、程式碼一起），在哪台機器跑都一樣。再設定 GitHub Actions：每次推程式碼，雲端自動開一台乾淨的機器，跑 lint、測試、build image、真的跑起來打一下，有一步紅就看得到。
**你沒有 Docker 怎麼辦**：CI 就是你的 Docker 練習場，它真的在跑。

## 關卡 10：上線

**情境**：手機用 4G 要開得到。
**做了什麼**：店放 Render、櫃台放 Vercel、倉庫放 Neon，全部免費方案。最關鍵的決定是**前後端同站**：櫃台不直接打店的網址，而是打自己網址的 `/api/...`，由 Vercel 在背後轉給 Render。對瀏覽器來說前後端是同一家，會員卡（cookie）才會被帶上。
**踩過的坑**：這一關踩的坑都記在 `DEBUGGING.md`，而且幾乎都是「瀏覽器的規則」而不是程式的問題（關卡 19 會講）。

## 關卡 11：維護

**情境**：半夜壞了，你只有 log 可以看。
**做了什麼**：三樣東西。看得到：每個請求一行 JSON log、每筆有編號（request id）、Sentry 會主動寄信告訴你爆了什麼。退得回去：Render 一鍵退版；倉庫的施工單壞了不要「退」，要「再開一張單修正」。進不來：CI 綠了才部署，main 不能直接推，一律走 PR。
**順便**：換簽通行證的密鑰不會把大家登出，因為會員卡跟密鑰無關，這是第 1 關設計的回報。

## 關卡 12：TanStack Query

**情境**：「使用者資料」這種東西是倉庫裡的副本，會過期、要重抓、要顯示載入中、兩個畫面同時要怎麼辦。以前全部手寫。
**做了什麼**：櫃台的狀態分兩種：「櫃台自己的」（通行證、提示文字）留在 Zustand；「倉庫資料的副本」交給 TanStack Query，它管什麼時候抓、抓到存哪、載入中、錯誤、重抓。
**判斷方法**：這東西有沒有一個後端的正本，而且你想讓畫面跟著正本走？有就交給 TanStack Query。

## 關卡 13：工程品質基線

**情境**：「這是教學模板」不是降低標準的理由，你要求專業水準。
**做了什麼**：裝齊一個專業團隊的基本配備：型別檢查（pyright、TypeScript strict）、自動排版（ruff format、Prettier）、套件自動更新（Dependabot）、固定 Python 和 Node 版本。順手修了四個「能跑但不專業」：加密密碼時整家店會卡住 100 毫秒（丟到另一條執行緒）、從回應時間可以猜出哪些帳號存在、兩人同時註冊同一個 email 會 500、通行證沒強制要有過期時間。
**四種檢查各抓什麼**：lint 抓寫法、formatter 抓排版、型別檢查抓「有時候是 None」、測試抓行為。

## 關卡 14：表單

**情境**：表單的「規則是什麼」和「欄位怎麼管」全部手寫，欄位一多就亂。
**做了什麼**：規則交給 Zod（一份 schema 同時給型別和驗證，等於前端的 Pydantic），欄位狀態交給 React Hook Form。元件只剩「送出後要做什麼」。
**原則**：前端的規則只是「提早告訴客人」，後端的規則才是「不信任櫃台」。兩份要一樣。

## 關卡 15：樣式

**情境**：樣式寫在每個元件的 `style={{...}}` 裡，不能寫 hover、不能做深色模式。
**做了什麼**：改用 Tailwind（樣式寫在 class 名字裡），重複的組合包成四個小元件（輸入框、按鈕、提示、警示），加了深色模式。順手修了一個端對端測試抓到的 bug：密碼打錯後按鈕卡在灰色。

## 關卡 16：前端測試

**情境**：店有 50 幾個測試，櫃台一個都沒有，改攔截器只能用眼睛看 Network。
**做了什麼**：Vitest 跑測試，MSW 當假的店（在網路層攔截請求回假資料，程式碼一行不用改）。測了攔截器的五條路、守門員的三種狀態、登入表單。拿掉 single-flight 或 `_retry`，測試會紅。
**和店的測試對照**：假的店 = 測試用倉庫，`afterEach` 清乾淨 = 每個測試前清空資料表。

## 關卡 17：登入頻率限制

**情境**：登入端點沒有限制，就是一台免費的密碼猜測機。
**做了什麼**：同一個 IP 每分鐘最多 10 次登入或註冊，超過回 429。最難的是「客人的 IP 是哪個」：請求經過 Vercel 和 Render 兩層代理，程式直接看到的是代理的 IP，所有人看起來都一樣；而標頭最左邊的 IP 是客人自己能填的，不能信。規則是從右邊跳過已知的代理層數取下一段。

## 關卡 18：SQL 與資料庫

**情境**：你一直透過工具（ORM）用倉庫，沒親眼看過倉庫怎麼找東西。AI 寫的查詢「能跑」很容易，「資料多了還快」要你自己看得懂。
**做了什麼**：沒改程式，給你一份實驗：灌 5 萬筆假資料，看「有目錄」（索引）和「沒目錄」找同一筆差幾十倍；看兩個人同時改同一筆時誰先誰後（鎖）；看「問 21 次」和「問 1 次」的差別（N+1）。
**一句話**：索引是另外維護的目錄，不是每個欄位都該有；每一趟問倉庫都是一次新加坡來回。

## 關卡 19：HTTP 與瀏覽器規則

**情境**：關卡 10 踩的每一個坑都不是 FastAPI 或 React 的問題，是瀏覽器的規則，換任何技術棧都一樣。
**做了什麼**：把這個專案用到的每個狀態碼（400 跟 401 為什麼不能混用）、會員卡 cookie 的五個屬性各擋什麼、CORS 為什麼不是安全機制、快取會把 A 的資料給 B，全部對回你踩過的坑。順手加了一行：所有 API 回應都「不准快取」。
**動手**：全部用 curl 看原始的請求和回應。

## 關卡 20：讀 log 與除錯

**情境**：AI 說「修好了」，你要能自己確認。
**做了什麼**：一套固定的除錯流程（先問哪一段壞、看錯誤最後幾行、重現、縮小範圍、用工具不用眼睛掃、修完加測試），然後給你五個真的壞掉的版本（patch 檔）練：有的測試會紅、有的 `alembic check` 會紅、有一個**全部綠但東西壞了**。知道哪種是哪種，才知道什麼時候該相信 CI、什麼時候要自己開瀏覽器。

## 關卡 21：本機整套與 E2E

**情境**：關卡 9 把店做成一張光碟（image），關卡 10 把光碟拿到 Render 去放。但在自己電腦上，光碟、倉庫（Postgres）、連線字串還是要一個一個手動擺好才跑得起來。
**做了什麼**：寫一張「開店清單」（`infra/compose.yaml`）：倉庫先開、確認能接單了才開櫃台、連線字串直接寫服務名。一個指令整套起來，再用一個真的瀏覽器（Playwright）把「註冊、登入、重新整理還在、登出」走一遍，三條路都綠才算這家店能營業。
**為什麼重要**：這張清單就是關卡 23 Kubernetes 清單的縮小版；E2E 是關卡 16 元件測試補不到的那一段：cookie 在真瀏覽器裡到底帶不帶。
**動手**：Mac 上 `docker compose up`、`npm run test:e2e`；沒有 Docker 的機器看 CI 的 `compose`、`e2e` 兩個 job。

## 關卡 22：指標與追蹤

**情境**：關卡 11 給店裡裝了日誌（每筆交易一行）和警報器（Sentry）。但老闆問「這小時平均多快？錯誤率多少？」得翻幾萬行日誌加總；問「這筆 120 毫秒花在哪？」日誌只說「總共 120」。
**做了什麼**：兩樣新東西。**指標**：程式自己數「幾筆請求、多快、幾筆錯」，Prometheus 每 5 秒來抄一次數字，Grafana 畫成圖，圖的設定檔也進 git。**追蹤**：把一個請求畫成一棵樹，最外層是 HTTP，底下是它做的每一句 SQL，各自花多久；日誌裡多一個 trace_id，兩邊互相找得到。
**為什麼重要**：三種訊號各管一件事：日誌找單一請求、指標看趨勢與告警、追蹤看一個請求走了哪幾站。而且用的是 OpenTelemetry 標準：送到本機的 collector、Grafana Cloud、Datadog 都只改環境變數，程式不動。
**動手**：Mac 上 `--profile observability` 起來看 localhost:3000 的儀表板和 collector 的 log；沒 Docker 看 CI 的 `observability` job。選配：把 Render 的 trace 送到 Grafana Cloud 免費方案。

## 關卡 23：Kubernetes

**情境**：Render 幫你做了很多事：起容器、掛了重啟、換版時先起新的再關舊的、health check。你只看得到結果，不知道是誰在做、怎麼做。
**做了什麼**：把同一張光碟（image）交給 Kubernetes（本機用 kind，一個叢集就是一個 Docker 容器）：寫清楚「我要 2 個副本、活著的定義、能服務的定義、要多少 CPU 記憶體、換版時舊的要等新的 Ready 才能關」。遷移獨立成一個 Job 先跑。然後親眼看：換版期間連續打 80 次全部 200；退版一個指令；故意給一個不存在的版本，新 pod 起不來、舊 pod 繼續服務、流量根本沒切過去。
**為什麼重要**：這些就是 Render 的「自動」背後的事。清單進 git，別的專案直接複製；面試時「零停機怎麼做到」可以指著 `maxUnavailable: 0` 和 `preStop` 說。
**動手**：Mac 上 `brew install kind kubectl` 照 COACHING 的指令一步步做；沒 Docker 看 CI 的 `k8s` job。線上仍是 Render，這關不換平台。

## 整個專案一句話

一家店，客人進門看通行證（快、不翻名冊）、換通行證看會員卡（翻名冊、會輪替、被偷能全部作廢）；櫃台和店在同一個網址下（cookie 才帶得上）；倉庫的結構用施工單管；每次改東西都有機器幫你檢查、綠了才上線；壞了有 log 和退版。前 12 關是把這家店開起來，13 到 17 是把它做到專業水準，18 到 20 是你要帶走的三樣基本功：看得懂倉庫、看得懂瀏覽器規則、找得到問題。
