# PLAN-FULLSTACK.md：轉全端的差距清單與下一階段路線

> 狀態：v1（2026-10-27）。接在 `PLAN.md`（關卡 0～20）、`PLAN-INFRA.md`（關卡 21～25）之後的第三份計畫。
> 回答三個問題：這個 repo 之後，距離「能自己規劃一個新專案、和 AI 合作把它做完」還差什麼；每一項業界有多需要；怎麼排進去而不硬塞。
> 讀法：第 1 節五分鐘看結論；第 2 節是清單；第 3 節是調整後的路線；第 4 節是帶每一項的規矩；第 5 節是和 AI 合作的固定循環（學習者的最終目標）；第 6 節是進度。
> 這份文件不取代 `HANDOFF.md`：學習者是誰、帶法、已經定的事都在那裡。這裡只管「接下來做什麼、為什麼、照什麼順序」。

## 0. 排法的前提（從 `HANDOFF.md` 第 1 節來，每一項都照這個排）

- **背景**：JS/TS 出身、Python 新手。程式邏輯看得懂（劇本型的程式），卡在名詞和看不見的東西（準備型的程式、系統表、網路上的請求長怎樣）。→ 每一項開始前先給名詞表，每個名詞一個比喻；準備型的程式可以略過，明講什麼時候回來。
- **機器**：平日 Windows VM 沒 Docker；週末 Mac 有 Docker；每次開機都是乾淨的。→ 需要 Docker 的排週末，平日做不用 Docker 的；每項都有 Mac 路線和 VM 路線。
- **時間**：每天約 4 小時。→ 一項一週內做得完，做不完就拆。
- **錢**：全部免費；會跳付費頁的先講，由他決定。→ 第 2 節的「費用」欄，⚠️ 的要先講。
- **帶法**：一次一個指令、他貼輸出、從輸出講（`COACHING.md` 第 1 節）。
- **目標**：之後能自己規劃新專案並與 AI 合作完成。→ 所以第 3 節的每一塊都是「他先規劃、AI 做、他驗收、他 review」，不是「AI 全做他看」。練的是指揮與驗收，但關鍵的二十行要讀得懂。

## 1. 結論（五分鐘版）

**已經有的、而且符合現代實務**：async 後端、驗證、遷移、refresh 輪替與重用偵測、頻率限制、結構化 log、健康檢查分兩種、Sentry、12-factor 設定、測試打真資料庫、lint 與型別檢查、現代 React 工具鏈、元件測試與 E2E、非 root 的 Docker、CI 全綠才合併、Dependabot、SAST 與套件漏洞掃描、同站代理、退版 runbook、compose、指標與追蹤、Kubernetes、outbox 與 Kafka、每一塊都有 CI job 證明。這比多數教學專案和新人作品集完整，尤其是「證明它會動」和「壞了怎麼修」這兩件事。

**差距分三類**：

| 類 | 是什麼 | 大小 | 補在哪 |
| --- | --- | --- | --- |
| A | **應用的廣度**：業務資料表、授權、分頁、複雜前端、API 規範、需求拆解、code review | 最大，沒有它不算全端 | 練習專案（`CHAIN.md` 環 1～7） |
| B | **常見元件與登入的洞**：安全標頭、忘記密碼、OAuth、角色權限、Redis、檔案上傳 | 中，面試常問 | 本 repo 的延伸關卡 26～30，做完搬進練習專案 |

**路線調整（和原本的差別）**：原本是「重帶走完 20 → 關卡 21～24 → 練習專案」。改成「重帶走完 20 → **練習專案（平日）和關卡 21～24（週末）平行** → 延伸關卡 26～30 穿插 → 雲」。理由：練習專案決定他是不是全端，應該最早開始；21～24 要 Docker，只能週末，兩邊互不相依可以平行；延伸關卡的東西（忘記密碼、OAuth、角色）練習專案會直接用到，做完就搬。

**刻意不做的**：GraphQL/tRPC、WebSocket、Monorepo 工具鏈、i18n，看職缺再說；Terraform 等有雲再說。

## 3. 調整後的路線

```
現在 ──▶ Phase 0 重帶 7～20（1～2 週）                      ← 不變，照 COACHING
            │  走到關卡 11 時順手做 B10（備份還原演練）
            ▼
         Phase 1 練習專案 v1（平日，4～6 週）                ← 提前：原本排在 21～24 之後
            │  CHAIN 環 1～7；Node/TS + Next.js；功能含 A1～A6；每個功能走第 5 節的循環；AI 當 reviewer（A8）
            ├─ 平行：Phase 1' 關卡 21～24（週末 Mac，一週一關）← COACHING 腳本已經有
            ├─ 穿插：Phase 2 延伸關卡 26～30（本 repo，每關半天到一天）
            │          順序：26 安全標頭 → 29 角色 → 27 忘記密碼 → 28 OAuth → 30 Redis
            │          做完一關就搬進練習專案（這就是 CHAIN 附錄 A 的搬家）
            ▼
         Phase 3 雲（1～2 週）                               ← 新
            │  練習專案第二次部署：GCP Cloud Run 或 AWS；C1；之後 C2
            ▼
         Phase 4 收尾
               ARCHITECTURE 第 6 節的 60 秒說法補上練習專案；練習專案自己的 ARCHITECTURE；履歷
```

**為什麼練習專案提前**：差距 A 是三類裡最大的，而且只有練習專案補得了；21～24 需要 Docker 只能週末，兩邊互不相依；延伸關卡做出來的東西練習專案會直接用到，先有專案才有地方搬。

**為什麼練習專案用 Node/TS + Next.js**：他的背景是 TS，Node 後端上手快；台灣職缺 Next.js 比 Vite SPA 常見；本 repo 的觀念（同站、refresh 輪替、遷移、CI、runbook）全部能搬，`CHAIN.md` 每環都寫了換棧對照。這樣履歷上兩套技術棧都有。**如果他想繼續用 Python**：也行，FastAPI 現成，差距 A 一樣補得到，只是 A9、A10 留著。開 Phase 1 前問他一次，決定了就不換。

**延伸關卡 26～30 怎麼做**：編號接在路線圖最後（`HANDOFF.md` 第 2 節允許「教學用的延伸關卡」做在本 repo），照 `HANDOFF.md` 第 3 節的格式產出（LEARNING 一節、PLAIN 一段、COACHING 一個腳本），AI 做、他驗收，和關卡 21～25 的做法一樣。每一關都不碰練習專案；搬過去是練習專案的一個 PR。

**什麼時候可以說「我是全端」**：練習專案上線、有 3 個以上真功能、每個功能都有授權和測試、CI 綠才部署、RUNBOOK 和 ARCHITECTURE 自己寫、能用 60 秒講每一塊、至少一次部署到真的雲。這張清單就是 Phase 4 的驗收。

## 4. 帶每一項的規矩（給帶的人）

1. **先名詞、再在哪看、最後邏輯**。第 2 節每一列的「開始前要先懂的名詞」是最低限度；每個名詞一個比喻，不先講就不能拿來用（`COACHING.md` 第 1 節）。
2. **一次一步、他貼輸出**。新項目第一次做都走仔細關（1～2 小時）；搬進練習專案時走快速關。
3. **準備型的程式可以略過**（conftest、middleware、框架設定），明講「現在不用懂，什麼時候回來，怎麼抄」；劇本型的程式（路由、測試、元件）要讀得懂。
4. **付費門檻先講**。第 2 節 ⚠️ 的項目，動手前說「這步可能要卡／要錢，免費替代是＿＿」，由他決定（`AGENTS.md`）。
5. **每項結束要有證明**：一個 CI job、一個網址、或一個指令的輸出。沒有證明不算完成（`ARCHITECTURE.md` 的原則）。
6. **每項結束他寫三句**：解決什麼、怎麼證明、下一步。寫進練習專案的 ARCHITECTURE 或本 repo 第 6 節的表。
7. **不要替他做 A7 和 A8**：需求他寫、計畫他看懂才動工、review 他做。AI 的角色是把他的需求變成計畫和 PR，不是替他決定要做什麼。

## 5. 和 AI 合作做一個功能的固定循環（學習者的最終目標，練習專案每個功能都走一遍）

| 步 | 誰做 | 做什麼 | 產出 |
| --- | --- | --- | --- |
| 1 需求 | **他** | 用自己的話寫：使用者故事三句（誰、想做什麼、為了什麼）、驗收標準三條（打開什麼、看到什麼、不能發生什麼） | 一段文字，貼給 AI |
| 2 計畫 | AI | 回一份計畫：改哪些檔、資料表怎麼改、API 長什麼樣、前端哪一頁、要哪些測試、風險與取捨。**不動手** | 計畫 |
| 3 看懂 | **他** | 讀計畫，不懂的名詞先問到懂；不同意的取捨提出來。**計畫沒看懂不准動工** | 修過的計畫 |
| 4 拆任務 | 他和 AI | 拆成 PR 大小（一個 PR 一件事：遷移一個、API 一個、前端一個、E2E 一個） | 任務清單 |
| 5 做與驗收 | AI 做，**他**驗 | AI 開分支、做一個 PR、CI 綠；他照第 1 步的驗收標準親手驗（指令、畫面、測試），再 review diff，至少讀懂關鍵的二十行，看不懂的問 | 一個合併的 PR |
| 6 收尾 | **他** | 更新 RUNBOOK／DEBUGGING（踩到的坑）、ARCHITECTURE（新的一塊）；用三句話講這個功能 | 文件 + 三句話 |

**對話範本（複製貼上）**

> 規劃：「先讀練習專案的 `AGENTS.md` 和 `ARCHITECTURE.md`。我要做的功能：＿＿＿（使用者故事三句、驗收標準三條）。先給我計畫：改哪些檔、資料表、API、前端頁、測試、風險。不要動手。計畫裡每個我可能不懂的名詞用一句白話解釋。」
>
> 做一個 PR：「照上面計畫的第 N 個任務做，只做這一個。開分支、一個 commit、推上去、開 PR。CI 綠了告訴我：我要怎麼親手驗收（指令和預期輸出）、diff 裡哪二十行是關鍵、為什麼這樣寫。做完列出你注意到但沒做的事。」
>
> Review：「我看了 diff，第 ＿ 行為什麼要＿＿？如果改成＿＿會怎樣？」（他問，AI 答；答案裡有新名詞就再問）
>
> 卡住：「症狀：＿＿＿（貼 log）。先查 `DEBUGGING.md`，沒有就分段確認，先講根本原因再修，修好加進 `DEBUGGING.md`。」

**他一定要自己做、不能交給 AI 的事**：寫需求、看懂計畫、驗收、review、決定取捨、決定付費、按下合併。這七件事就是「能自己規劃並與 AI 合作完成新專案」的定義。
